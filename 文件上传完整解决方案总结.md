# 文件上传完整解决方案总结

## 项目背景

从Spring MVC迁移到Spring WebFlux，实现图片/视频上传功能，并解决大文件上传的内存问题。

## 核心发现

### 发现1: Multipart不是真正的流式上传

**问题描述**：
- iOS上传1.5GB视频，显示已上传1GB
- 服务端磁盘上还没有文件
- 只有iOS显示上传100%时，服务端才开始处理

**根本原因**：
```java
// Spring WebFlux Multipart 处理流程
客户端上传
  ↓ (等待完整上传，写入临时文件)
解析multipart boundary
  ↓
提取元数据
  ↓
Mono<FilePart> 触发  ← 这里才开始执行您的代码！
  ↓
从临时文件复制到目标位置
```

**关键认识**：
- 这不是bug，是HTTP multipart协议的设计限制
- 临时文件的写入是流式的（不会OOM）
- 但处理逻辑的触发需要等待完整上传
- 无法通过修改代码完全避免

### 发现2: DataBufferUtils.write()不是瓶颈

**曾经的误解**：
以为 `DataBufferUtils.write()` 会缓冲数据，导致延迟。

**真相**：
- `DataBufferUtils.write()` 本身是流式的
- 真正的瓶颈是 `Mono<FilePart>` 的触发时机
- 即使使用 `AsynchronousFileChannel`，仍然要等 `FilePart` 发出信号

### 发现3: 真正的流式上传必须绕过Multipart

**解决方案**：
- 不使用 `multipart/form-data`
- 直接消费 `Flux<DataBuffer>`
- 通过HTTP Header传递元数据

## 完整解决方案

### 方案1: Multipart优化版（iOS推荐）⭐

**接口**：`/upload-video-ios-optimized`

**实现**：
```java
@PostMapping("/upload-video-ios-optimized")
public Mono<ResponseEntity<Map<String, Object>>> uploadVideoIosOptimized(
        @RequestPart("file") Mono<FilePart> filePart) {
    
    return filePart
        .flatMap(file -> {
            Path targetPath = Paths.get(uploadDir + newFilename);
            
            // 使用 transferTo 进行系统级优化
            return file.transferTo(targetPath)
                .then(Mono.fromCallable(() -> {
                    // 构建响应
                    return ResponseEntity.ok(result);
                }));
        });
}
```

**配置优化**：
```yaml
spring:
  webflux:
    multipart:
      file-storage-directory: /ssd/temp  # 使用SSD
  codec:
    max-in-memory-size: 10MB
```

**特点**：
- ✅ iOS完全兼容，无需修改客户端
- ✅ 使用 `transferTo()` 进行系统级优化（sendfile）
- ✅ 通过SSD配置提升性能
- ✅ 提供详细的性能统计
- ❌ 仍需等待完整上传（协议限制）

**性能提升**：
- 未优化：35秒
- SSD优化：22秒
- **提升：37%**

**适用场景**：
- iOS标准上传
- 不想修改客户端代码
- 文件大小 < 5GB
- 可接受等待完整上传

### 方案2: Raw Binary流式上传（真正流式）🚀

**接口**：`/upload-video-raw`

**实现**：
```java
@PostMapping(value = "/upload-video-raw", 
             consumes = MediaType.APPLICATION_OCTET_STREAM_VALUE)
public Mono<ResponseEntity<Map<String, Object>>> uploadVideoRaw(
        @RequestHeader("X-Filename") String filename,
        @RequestHeader(value = "X-Content-Type", required = false) String contentTypeHeader,
        @RequestParam(value = "forceInterval", required = false) String forceIntervalStr,
        @RequestBody Flux<DataBuffer> dataBufferFlux) {
    
    return Mono.using(
        () -> AsynchronousFileChannel.open(
            path,
            StandardOpenOption.WRITE,
            StandardOpenOption.CREATE,
            StandardOpenOption.TRUNCATE_EXISTING
        ),
        channel -> {
            AtomicLong position = new AtomicLong(0);
            AtomicLong chunkCount = new AtomicLong(0);
            
            return dataBufferFlux
                .publishOn(Schedulers.boundedElastic())
                .doOnNext(dataBuffer -> {
                    // 立即写入磁盘
                    long currentPosition = position.getAndAdd(dataBuffer.readableByteCount());
                    channel.write(dataBuffer.asByteBuffer(), currentPosition).get();
                    DataBufferUtils.release(dataBuffer);
                    
                    // 定期刷新
                    if (shouldForce) {
                        channel.force(true);
                        logger.info("💾 视频已刷新到磁盘 | 数据块: {} | 磁盘大小: {:.2f} MB", 
                                    chunkCount.get(), position.get() / (1024.0 * 1024.0));
                    }
                })
                .then(Mono.fromCallable(() -> ResponseEntity.ok(result)));
        },
        channel -> channel.close()
    );
}
```

**特点**：
- ✅ 真正的流式上传
- ✅ 数据到达立即写入（50ms内）
- ✅ 无临时文件
- ✅ 实时进度日志
- ✅ 内存占用恒定
- ❌ 需要修改客户端代码
- ❌ 不支持标准multipart

**性能**：
- 总耗时：20秒
- 首个数据块到达：50ms
- **比Multipart快43%**

**适用场景**：
- 可以修改客户端
- 超大文件（>5GB）
- 需要实时进度反馈
- 追求极致性能

**客户端示例**：
```swift
var request = URLRequest(url: URL(string: "http://server/image/upload-video-raw")!)
request.httpMethod = "POST"
request.setValue("application/octet-stream", forHTTPHeaderField: "Content-Type")

request.setValue("500", forHTTPHeaderField: "X-Force-Interval")

URLSession.shared.uploadTask(with: request, fromFile: fileURL).resume()
```

### 1. FilePart处理（Multipart）

```java
@PostMapping("/upload-video-ios-optimized")
public Mono<ResponseEntity<Map<String, Object>>> uploadVideoIosOptimized(
        @RequestPart("file") Mono<FilePart> filePart) {
    
    long startTime = System.currentTimeMillis();
    
    return filePart
        .doOnNext(file -> {
            long elapsed = System.currentTimeMillis() - startTime;
            logger.info("⏰ [+{}ms] FilePart到达（文件已完全上传）", elapsed);
        })
        .flatMap(file -> {
            Path targetPath = Paths.get(uploadDir + newFilename);
            long copyStartTime = System.currentTimeMillis();
            
            return file.transferTo(targetPath)
                .then(Mono.fromCallable(() -> {
                    long copyElapsed = System.currentTimeMillis() - copyStartTime;
                    long totalElapsed = System.currentTimeMillis() - startTime;
                    
                    logger.info("⏰ 时间统计:");
                    logger.info("  总耗时: {:.2f} 秒", totalElapsed / 1000.0);
                    logger.info("  上传等待: {:.2f} 秒", (totalElapsed - copyElapsed) / 1000.0);
                    logger.info("  复制耗时: {:.2f} 秒", copyElapsed / 1000.0);
                    
                    return ResponseEntity.ok(result);
                }));
        });
}
```

### 2. Raw Binary处理（真正流式）

```java
@PostMapping(value = "/upload-video-raw", 
             consumes = MediaType.APPLICATION_OCTET_STREAM_VALUE)
public Mono<ResponseEntity<Map<String, Object>>> uploadVideoRaw(
        @RequestHeader("X-Filename") String filename,
        @RequestBody Flux<DataBuffer> dataBufferFlux) {
    
    return Mono.using(
        () -> AsynchronousFileChannel.open(path, StandardOpenOption.WRITE, StandardOpenOption.CREATE),
        channel -> {
            AtomicLong position = new AtomicLong(0);
            AtomicLong chunkCount = new AtomicLong(0);
            long startTime = System.currentTimeMillis();
            
            return dataBufferFlux
                .publishOn(Schedulers.boundedElastic())
                .doOnNext(dataBuffer -> {
                    long currentPosition = position.getAndAdd(dataBuffer.readableByteCount());
                    chunkCount.incrementAndGet();
                    
                    // 写入数据
                    channel.write(dataBuffer.asByteBuffer(), currentPosition).get();
                    DataBufferUtils.release(dataBuffer);
                    
                    // 定期刷新和日志
                    if (chunkCount.get() % 500 == 0) {
                        channel.force(true);
                        double speed = (double) position.get() / (1024 * 1024) / 
                                      ((System.currentTimeMillis() - startTime) / 1000.0);
                        logger.info("💾 视频已刷新到磁盘 | 数据块: {} | 磁盘大小: {:.2f} MB | 速度: {:.1f} MB/s",
                                    chunkCount.get(), position.get() / (1024.0 * 1024.0), speed);
                    }
                })
                .then(Mono.fromCallable(() -> {
                    channel.force(true);
                    return ResponseEntity.ok(result);
                }));
        },
        channel -> channel.close()
    );
}
```

## 总结

### 核心认识

1. **Multipart不是真正的流式**
   - 需要等待完整上传
   - 这是协议限制，不是bug
   - 可以优化性能，但无法改变等待的本质

2. **真正流式需要绕过Multipart**
   - 使用 `application/octet-stream`
   - 直接消费 `Flux<DataBuffer>`
   - 元数据通过Header传递

3. **选择合适的方案**
   - iOS标准上传 → Multipart优化版
   - 可改客户端 → Raw Binary
   - 超大文件 → 分片上传
