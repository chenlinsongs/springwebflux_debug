# Spring WebFlux 可视化对比

## 线程使用对比图

### Servlet 模式（同步阻塞）

```
时间轴 →

请求1: Thread-1  ━━━━━━━[等待DB 100ms]━━━━━━━[等待HTTP 200ms]━━━━━━━ 返回
                  ▲                        ▲                      ▲
                  占用                     仍在占用                 释放
                  线程                     线程                    线程
                  
请求2: Thread-2  ━━━━━━━[等待DB 100ms]━━━━━━━[等待HTTP 200ms]━━━━━━━ 返回

请求3: Thread-3  ━━━━━━━[等待DB 100ms]━━━━━━━[等待HTTP 200ms]━━━━━━━ 返回

线程池耗尽！→ Thread-4 [等待分配线程...] ← 请求4被阻塞
              Thread-5 [等待分配线程...] ← 请求5被阻塞

总耗时：300ms
线程使用：3个线程 × 300ms = 900ms·线程
资源消耗：3个线程 × 1MB = 3MB
问题：线程大部分时间在等待，浪费资源！
```

---

### WebFlux 模式（异步非阻塞）

```
时间轴 →

请求1: EventLoop-1  ─[创建Mono]─ 释放 ............... [数据到达]─[写回]
                     ▲          ▲                    ▲
                     1ms        立即                 自动触发
                     
请求2: EventLoop-1  ───────[创建Mono]─ 释放 ............... [数据到达]─[写回]
                                       ▲
                                       同一个线程！
                                       
请求3: EventLoop-1  ─────────────[创建Mono]─ 释放 ............... [数据到达]

请求4: EventLoop-1  ───[创建Mono]─ 释放 ...............
请求5: EventLoop-1  ─────[创建Mono]─ 释放 ...............
...
请求100: EventLoop-1  ─[创建Mono]─ 释放 ...............

总耗时：300ms（和Servlet一样，网络延迟不变）
线程使用：1个线程 × 5ms = 5ms·线程（节省了99.4%！）
资源消耗：1个线程 × 1MB = 1MB
优势：线程不等待，可以处理更多请求！
```

## 数据流转过程

### Servlet 请求流程

```
1. 客户端发送请求
        ↓
2. Tomcat 分配线程
        ↓
   ┌────────────┐
   │  Thread-1  │ ← 线程被占用
   └────────────┘
        ↓
3. 执行 Controller
        ↓
4. 调用 RestTemplate
        ↓
   [阻塞等待HTTP响应]  ← 线程在这里浪费
        ↓
5. 处理业务逻辑
        ↓
6. 返回响应
        ↓
7. 释放线程
   ┌────────────┐
   │  Thread-1  │ ← 线程被释放
   └────────────┘
```

---

### WebFlux 请求流程

```
1. 客户端发送请求
        ↓
2. Netty EventLoop 接收
        ↓
   ┌─────────────┐
   │ EventLoop-1 │
   └─────────────┘
        ↓
3. 执行 Controller
        ↓
4. 创建 Mono/Flux
        ↓
5. 注册回调
        ↓
6. 立即返回（线程释放）
   ┌─────────────┐
   │ EventLoop-1 │ ← 可以处理其他请求了
   └─────────────┘
        ↓
   [线程去处理其他请求]
        ↓
   [HTTP 响应到达]
        ↓
7. 触发回调
   ┌─────────────┐
   │ EventLoop-2 │ ← 可能是不同的线程
   └─────────────┘
        ↓
8. 处理业务逻辑
        ↓
9. 写回响应
        ↓
10. 完成（线程继续处理其他请求）
```

## 核心概念可视化

### Mono<T> - 单个值的承诺

```
           Mono<String>
          
     [创建]  [转换]  [获取]
        ↓      ↓      ↓
     ┌────────────────────┐
     │   "将来会有String"  │ ← 这是一个"承诺"
     └────────────────────┘
              ↓
        [订阅/触发]
              ↓
        "Hello World"  ← 最终的值
```

### Flux<T> - 多个值的流

```
           Flux<Integer>
          
     [创建]  [转换]  [订阅]
        ↓      ↓      ↓
     ┌────────────────────┐
     │   "将来会有很多值"   │
     └────────────────────┘
              ↓
         1 → 2 → 3 → 4 → 5 → 完成
         ↓   ↓   ↓   ↓   ↓
        可以逐个处理，不需要全部加载到内存
```

## 关键要点

### 1️⃣ WebFlux 不是让单个请求变快
```
Servlet:  请求 → [300ms] → 响应
WebFlux:  请求 → [300ms] → 响应  (一样快)
```

### 2️⃣ WebFlux 是让系统能处理更多请求
```
Servlet:  最多200个并发 (线程池限制)
WebFlux:  可以5000+个并发 (不受线程限制)
```

### 3️⃣ WebFlux 的威力在于并行调用
```
串行:  服务A(200ms) + 服务B(200ms) = 400ms
并行:  max(服务A, 服务B) = 200ms  ← 节省50%
```
